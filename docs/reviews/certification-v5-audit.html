Grades and what they mean

These are human-authored judgments, not automated scores or a measured percentage of migrated code. A 10 means complete, coherent and evidenced for the intended 5.0 learning outcome; 5 means partially adapted with material gaps; 1 means the necessary mechanism is essentially absent.

Chat delivery architecture7/10Seven course tools, five structured card types, shared module progress and chat-specific exercise instructions. Operational acceptance is blocked by the progress-tool exception.
Desktop visual design7/10Consistent cards, readable grouping, obvious next actions. Contrast, raw markup, small text and competing teaching/challenge content reduce clarity.
Mobile visual design3/10Critical lesson-title collapse at 320/390px; very narrow column. Action buttons can be reached by scrolling.

Prioritized findings

P1 · synchronization Fast completion responses can leave shared progress stale

When a tool call and its result arrive in one response batch, the new completion card mounts with a result already present. useCertificationSync treats that as historical replay and skips refresh. In the controlled browser reproduction, the card showed +125 XP but progress endpoint reads stayed at one before and after completion. This is a confirmed buffered-response UI case; live model streaming frequency is unmeasured. Use explicit live/history provenance and completion-event deduplication rather than result-on-mount as the distinction.

Evidence: module-complete; frontend/src/components/chat/CertificationCards.tsx:94; completion observation

P0 · functional Starting or continuing certification can fail immediately

The chat progress tool indexes prog["streak_days"], but the actual progress service has retired that response field. Calling the real tool with the real service serializer and a synthetic stored record raises KeyError: streak_days. The existing 44 focused backend tests pass because the tool fixture supplies the obsolete key. Fix the contract and add a test across the serializer/tool boundary before presenting certification as working end to end.

Evidence: backend/app/services/chat_tools.py:4839; backend/app/services/certification_service.py:153; reproduced contracts

P1 · visual Mobile lesson headers collapse into a vertical column of letters

At both 320px and 390px, the long lesson title is squeezed by the non-wrapping lesson-number/module label in a single flex row. The title becomes one or two characters per line and the label clips beyond the card. This can consume the entire first screen before the lesson starts. Page-level overflow metrics remain clean: clipping inside the chat is still a real defect. Stack the metadata below a wrapping title, remove inherited left indentation at narrow widths, and reduce the persistent navigation footprint.

Evidence: long-top-320; long-top-390; frontend/src/components/chat/CertificationCards.tsx:316

P1 · grading The interface can announce “All checks passed” beside a failed check

The Extraction Engine validator passes on the count of 15 fields, even if none match the expected fields and no extraction was executed. The real validator returned passed=true, one star, and a failed “Missing expected fields” check for 15 unrelated fields. The card trusts the top-level flag and prints “All checks passed.” Decide which checks are requirements and which are advisory, encode that distinction, and make the summary consistent with the rubric.

P1 · instruction The lab instructions refer to controls that are absent in chat

The Foundations overview visibly includes literal **Set Up Lab** and **Check Progress** markup. It says “click Set Up Lab below,” but the chat card offers lessons, a progress check, and a split-view button; provisioning requires asking the agent. The step list is semantically ordered but shows no visible numbering. Use surface-appropriate copy, render authored Markdown safely, and provide a real lab action that shows its provisioning state.

Lesson position metadata and per-module XP use #9ca3af on the pale card background. A representative lesson measured 2.45:1 for 12px text against the 4.5:1 automated threshold. Passing and completion greens also need review wherever flagged in the individual axe files. Darken the shared metadata/success tokens and verify every state; screenshots alone are not an accessibility conformance assessment.

P1 · pedagogy Chat drops the diagrams and does not render knowledge checks

All 74 lesson bodies currently match the panel export. However, the panel has eight diagram references that the export discards. Eighteen knowledge checks are exported, but CertLessonCard never renders their questions or answer controls. The tool tells the LLM to ask them, so the teaching depends on model compliance rather than a dependable course interaction. The fixture containing a real knowledge check produced zero occurrences of its question in the UI. Render the authored diagram and check deterministically; let the agent coach around them.

Evidence: knowledge-check-chat; panel-diagram-and-knowledge-check; frontend/scripts/export-lessons.mjs:53; frontend/src/components/chat/CertificationCards.tsx:303

P1 · continuity Chat and panel share module credit, but not a durable lesson position

The panel stores a numeric index in localStorage under user+module, with no course version. The chat lesson tool only reads content and does not persist lesson position. Opening the panel after chat lesson 3 starts at lesson 1 in the inspected fresh session. Inserting or reordering lessons can make a saved index point at a different lesson. Store stable lesson IDs and an enrollment-scoped server cursor; use the same cursor in both surfaces and across devices.

Evidence: chat-to-panel-resume; frontend/src/components/certification/LessonStepper.tsx:39; backend/app/services/chat_tools.py:4900

P1 · curriculum Two important lessons contradict the trust model

The introductory agentic lesson says every result has a quality score and implies more verification always increases the tier. The later QA lesson correctly says scores describe tested examples and new cases can lower them; unvalidated results may be Unscored. Separately, Advanced Nodes recommends Deep Analysis for checking arithmetic despite earlier advice never to trust LLM arithmetic. ResearchNode makes two LLM calls, not a deterministic calculation. Teach consistent quality limits and require calculator/code/spreadsheet or manual arithmetic verification.

Evidence: frontend/src/components/certification/modules.ts:87; frontend/src/components/certification/modules.ts:482; backend/app/services/workflow_engine.py:1285

P1 · credential integrity The rubric mostly verifies artifact presence, not demonstrated skill

Foundations aggregates fields and execution across a user’s artifacts. Extraction Engine awards higher stars for field count without validating the stated categorical/optional-field criteria. Multi-Step and Advanced Nodes can pass by configuration without a successful lab run. Output & Delivery can combine an output node from one workflow with execution of another. Validation & QA counts cases across templates and accepts a validation record without proving the learner examined failures. These are useful activity checks, but agent-generated artifacts make them weak evidence of learner competence. Bind each attempt to its lab, artifact revision, run and reviewed evidence.

Evidence: backend/app/services/certification_service.py:620; backend/app/services/certification_service.py:733; backend/app/services/certification_service.py:813; backend/app/services/certification_service.py:857

P1 · progression The panel gates modules, while the backend bypasses prerequisites

The service contains “TEMP: prerequisite check bypassed for review.” With empty progress, the later-module validator is still invoked. The panel uses a prerequisite lock and an explicit admin unlock flag, so the two entry points enforce different policies. Either deliberately permit self-paced order in both surfaces or enforce the published rule server-side with an explicit, audited admin override.

Evidence: backend/app/services/certification_service.py:306; frontend/src/components/certification/useModuleLock.ts:5; reproduced contracts

P1 · lifecycle There is no versioned enrollment, rubric, or credential

Progress is a single document keyed by user with a modules dictionary and a certified boolean. Lessons/exercises and MODULE_ORDER are read from the current application. Existing completion booleans survive changed content, while remaining modules are judged against new rules. Adding a module can leave an already-certified learner certified while the current module list is incomplete. The PDF is generated from the current progress record, not an immutable issuance record. This is insufficient to distinguish a 4.0 credential, the current hybrid course, and a completed 5.0 bridge.

Evidence: backend/app/models/certification.py:8; backend/app/services/certification_service.py:325; backend/app/routers/certification.py:25

P2 · consistency Counts, stars, and completion actions need one authoritative definition

AI Literacy says six lessons although it has nine; Thinking in Workflows says six but has seven; Workflow Design says six but has eight. Multi-Step’s third-star copy says four task types while the validator requires five. Several stars describe successful extraction or constrained fields that are not checked. The final chat card has no certificate-download action, while the panel does; the panel banner hardcodes 1850 XP although actual XP includes star bonuses (up to 2675). Generate labels and criteria from the versioned manifest and link the final chat card to the certificate.

How much has actually changed?

All 11 modules have chat-specific exercise instructions. All 74 exported lesson bodies match the panel source. Four dedicated lessons directly address agentic chat, chat-driven design, trust tiers and guided verification, spread across three modules. That is 4/74 dedicated lessons (5.4%), not a claim that only 5.4% of the curriculum is relevant: many older concepts remain useful. Four of the eight hands-on validators explicitly accept chat-era SearchSet/activity evidence. The rest can use workflows the agent creates, but that does not establish a new learning outcome.

The important distinction is delivery versus competence. Moving a lesson into a conversation is useful; certifying someone to supervise an agent requires assessing the decisions the person makes around that agent.

Module5.0 alignmentCritique and required update
0 · AI Literacy5/10One agentic lesson is a useful introduction; fix exaggerated quality claims. Add scope selection, source inspection and approval judgment. Reflection alone does not demonstrate those skills.
1 · Foundations6/10Chat-specific create/run exercise and SearchSet credit exist. Lessons still send the learner into a workflow editor. Grade the actual lab extraction and source-checked values.
2 · Thinking in Workflows4/10Process decomposition remains valuable. Add a decision between a one-off chat task, a project, a saved extraction/workflow and automation. Assess an applied choice.
3 · Workflow Design6/10A dedicated chat design lesson exists. Require the learner to identify and repair a bad proposed plan, approve the right scope and choose a human checkpoint.
4 · Extraction Engine5/10Chat proposing and guided verification appear in exercise steps. The count-based grader does not enforce the promised accuracy or field-configuration criteria.
5 · Multi-Step Workflows5/10The exercise can be authored/run from chat. Add approval review, inspection of actual step outputs, and recovery without repeating successful writes.
6 · Advanced Nodes3/10The exercise is mostly the existing node/parallelism lesson wrapped in chat. Fix the arithmetic guidance; teach tool boundaries and safe handling of unavailable capabilities.
7 · Output & Delivery4/10Editor handoff is a valid precision workflow, but it should be explicit and return cleanly to chat. Require opening and checking the actual delivered file from the same run.
8 · Validation & QA7/10Strongest update: trust tiers and guided verification are dedicated lessons. Add Unscored/stale/critical cases and require explaining a failing or regressed result.
9 · Batch Processing5/10Chat extraction on multiple documents counts. Teach document scope, partial failure and retry in chat; verify the intended batch and sampled source values.
10 · Governance4/10Sharing/examiner concepts have useful updated language; submission-based completion avoids waiting on an examiner. Missing assessed project/team scope, data boundaries, automation approvals and artifact ownership.

Recommended 5.0 learning outcomes

  1. Orient and scope: pick the right team/project, distinguish attached documents from knowledge-base and web sources, and confirm what the assistant can access.
  2. Supervise proposed work: inspect a proposed extraction/workflow/automation; correct a deliberate mistake; approve or decline a concrete change.
  3. Verify evidence: open source passages, correct a wrong field, create grounded test cases, distinguish Unscored, measured quality and examiner approval.
  4. Recover safely: handle a failed tool, partial batch and interrupted conversation without duplicating completed changes.
  5. Deliver and govern: inspect the output, choose sharing scope, understand ownership and ongoing automation behavior.
  6. Demonstrate mastery: complete a short unfamiliar capstone with one wrong proposed action and one bad result; the learner must detect both. Agent assistance is allowed; assessed decisions must belong to the learner.

Keep the existing 11-module structure initially if that reduces disruption, but rewrite the outcomes and evidence. A later dedicated “Agentic Operator” foundation plus “Workflow Architect” advanced track may fit the product better than requiring all everyday chat users to master advanced nodes.

Updating the program while people are taking it

Recommended policy: preserve earned credit, pin an enrolled learner’s assessed requirements, and offer an explicit 5.0 bridge. Do not silently change what a completed credential means and do not reset everyone’s progress.

Learner stateRecommended behavior
Already certifiedKeep the original credential and completion date. Offer a separate “Vandalizer 5.0 update” bridge. Do not automatically relabel the old credential as 5.0 or remove it when adding requirements.
Started, not certifiedPin the current enrollment to an immutable legacy course snapshot. Offer “Continue your current course” and “Move to 5.0”; show exactly what carries over and what remains before accepting the move.
Mid-lesson, assessment or labKeep the attempt’s lesson/rubric revision and submitted answers intact. Apply migration at a safe checkpoint, never halfway through submission or grading.
Not started / new learnerEnroll in the published 5.0 version after its acceptance gates pass.
Version unknown in legacy recordsMark provenance as legacy/unversioned. Recover historical release evidence if available; otherwise do not invent a 4.0/5.0 label. A snapshot taken now preserves the current course but cannot reconstruct what someone saw months ago.

What can change without requiring a new enrollment?

  • Editorial patch: typo, broken link, accessibility or layout correction with unchanged objectives and rubric. Publish a patch and record its change note; keep results.
  • Optional enrichment: new example or reference. Label it optional and do not change the completion denominator.
  • Material change: new outcome, mandatory lesson, changed pass/star criteria, exercise dataset or tool behavior that affects assessment. Publish a new course/rubric revision; existing attempts keep their pinned requirements.
  • Urgent incorrect guidance: display a correction immediately and record acknowledgment when needed. If assessment is unsafe or no longer executable, pause only that activity and provide an equivalent replacement; preserve unaffected credit.

The 5.0 bridge

Proposed scope: roughly 45–60 minutes, to be checked with a small learner pilot. Three short units: (1) scope and approval decisions; (2) source verification and quality limits; (3) interruption/partial-failure recovery and safe delivery. Finish with the unfamiliar capstone. Grant equivalent credit for genuinely unchanged outcomes using an explicit mapping; require the new outcomes even for legacy graduates. No duplicate XP for transferred credit.

CourseVersion: id, status, product_version, module/lesson IDs,
  content hashes, rubric versions, exercise revisions, change notes
Enrollment: user_id, course_version_id, status, lesson_cursor,
  started_at, migrated_from, migration_choice_at

  lab/artifact/run IDs, source evidence, answers, grade, timestamps
CreditTransfer: from enrollment/attempt, to enrollment/outcome,
  equivalence-rule revision, reason
Credential: immutable issuance ID, user, course version,
  demonstrated outcomes, issued_at, supersedes (optional)

Use immutable published manifests and draft/review/publish states. Promote content, exercise data, tool payloads and grading together. Add optimistic concurrency or an append-only event ledger and idempotency keys for completion/XP. Index active enrollment intentionally; the current user-only progress lookup is not an enrollment model. Key completion messages by credential/enrollment version: the existing once-per-user email flag would otherwise suppress a future bridge celebration.

Learner-facing copy

Vandalizer 5.0 training is available. Your completed work is saved. You can finish your current course or move to the updated course with eligible credit carried over. Review your remaining requirements before choosing.

Show “Course version,” last saved lesson, carried-over credit and newly required work in both chat and the panel. Define a supported legacy finish window only after checking actual cohort activity and support capacity; 90 days could be a starting proposal, not an announced deadline. No communications were sent during this review.

Implementation sequence and acceptance gates

  1. Repair the active experience: progress serializer/tool contract; mobile header; contrast; Markdown/control copy; grading summary; prerequisite consistency. Acceptance: real tool/service contract tests, 320/390/768/1440 captures, focus/scroll checks and a real local start/resume path.
  2. Freeze and identify the current course: snapshot lesson/exercise/rubric definitions; inventory completed, active and unstarted learners; back up progress and dry-run mappings. Report unknown provenance instead of guessing.
  3. Add enrollment/version support before changing required outcomes: stable lesson IDs, server cursor, versioned attempts, credit mappings and immutable certificates. Acceptance: old and new cohorts coexist; mid-attempt updates, cross-device resume, duplicate/concurrent submissions and rollback preserve credit.
  4. Author and assess 5.0: update each module above, deterministic knowledge checks/diagrams, evidence-bound practical grading and the bridge capstone. Acceptance: a learner can succeed via chat, editor, or a mixed route with equivalent evidence; a deliberately wrong result or unrelated artifact cannot earn credit.
  5. Pilot and publish: pilot with a new learner, a halfway learner and a legacy graduate; check completion time, rescue requests and quality of decisions. Publish the new version only after review, then offer cohort-specific choices. Rollback changes the default enrollment version without deleting attempts or credentials.

Measure course-start failures, actual next-lesson resume, grading disagreement, module abandonment, bridge opt-in/completion and support requests. Instrument by course/enrollment version without logging private document contents.
